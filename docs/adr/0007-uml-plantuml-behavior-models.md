# Динамическое поведение моделируется на UML в текстовой нотации PlantUML

## Контекст и постановка задачи

Структура FitSchedule (модули, данные, развёртывание) описана в SDD 0.2 моделями SysML v2. Для ЛР5 нужна модель
динамического поведения: варианты использования с описаниями, диаграммы активности, состояний и последовательности,
согласованные между собой и с SRS. Модель должна храниться в Git рядом с документацией, проверяться через pull
request (REQ-MAINT-001) и читаться без платных инструментов. На каком языке и в каком виде вести эти диаграммы и как
обеспечить связь между ними?

## Драйверы решения

* все четыре вида диаграмм поведения UML 2.5 с полной нотацией (`include`/`extend`, дорожки, вложенные состояния,
  комбинированные фрагменты `alt`/`loop`/`break`/`ref`);
* текстовый формат: различия видны в diff и ревью pull request;
* бесплатные инструменты и генерация PNG одной командой;
* трассируемость «требование → прецедент → диаграмма → представление SDD».

## Рассмотренные варианты

* PlantUML (`.puml`) с генерацией PNG;
* Mermaid в Markdown;
* SysML v2 (`use case def`, `action def`, `state def`) — продолжение моделей ЛР3–ЛР4;
* графический редактор (draw.io, StarUML).

## Итог решения

Выбран вариант «PlantUML», потому что только он даёт полную нотацию UML для всех четырёх видов диаграмм в текстовом
виде и рекомендуется заданием ЛР5 (расширение PlantUML для VS Code).

### Последствия

* Хорошо, потому что исходный текст диаграмм хранится в `docs/uml/diagrams`, а изменения видны в pull request.
* Хорошо, потому что PNG пересобираются командой `java -jar plantuml.jar -tpng -o ../img docs/uml/diagrams/*.puml`.
* Плохо, потому что в репозитории два языка моделирования: структура — SysML v2, поведение — UML.
  Смягчение: имена сущностей, статусов и операций совпадают в обеих моделях (см. «Механизмы связи»).
* Плохо, потому что PNG нужно пересобирать вручную после изменения `.puml`.

### Подтверждение

При ревью pull request проверяется, что каждому изменённому `.puml` соответствует обновлённый PNG в `docs/uml/img`,
а имена статусов на диаграммах состояний совпадают с перечислениями `BookingStatus`, `WaitlistStatus` модели
`docs/sdd/models/data-model.sysml`. После начала реализации (I3) переходы `state-booking` проверяются тестами
`BookingPolicyTest` и `WaitlistServiceTest`.

## Плюсы и минусы вариантов

### PlantUML

* Хорошо, потому что поддерживает все нужные элементы нотации, включая дорожки, `fork`, вложенные состояния,
  `create`/`destroy`, `ref` и сообщения через gate.
* Хорошо, потому что бесплатен и работает локально (Java + jar или расширение VS Code).
* Нейтрально, потому что раскладка автоматическая и иногда требует подсказок (`left to right direction`).

### Mermaid

* Хорошо, потому что GitHub отображает диаграммы прямо в Markdown.
* Плохо, потому что нет диаграммы вариантов использования и неполная нотация диаграмм активности.

### SysML v2

* Хорошо, потому что один язык со структурными моделями SDD.
* Плохо, потому что задание ЛР5 требует UML-диаграмм, а графическое отображение SysML v2 поведения в бесплатных
  инструментах ограничено.

### Графический редактор

* Хорошо, потому что раскладку можно настроить вручную.
* Плохо, потому что бинарный или XML-формат плохо читается в diff, а модель расходится с текстом документации.

## Дополнительная информация

### Механизмы построения диаграмм

1. **Прецеденты.** Для каждого функционального требования SRS 0.2, входящего в версию 1.0, выделено событие внешнего
   мира и инициатор: человек (Посетитель, Администратор), абстрактный Пользователь для общего поведения трёх ролей
   и **Время** — для напоминаний и отметки посещений. Повторяющееся поведение вынесено во включаемые прецеденты
   (`<<include>>`: UC-07 «Проверить доступность», UC-09 «Продвинуть лист ожидания», UC-19 «Уведомить участников»),
   необязательное — в расширения с точкой расширения (`<<extend>>`: UC-04, UC-06, UC-11, UC-16). Каждый прецедент
   описан потоком событий: краткое описание, предусловия, основной и альтернативные потоки, постусловия
   (`docs/uml/use-cases.md`).
2. **Активность.** Строится по потоку событий прецедента: каждый шаг основного потока — действие, каждый
   альтернативный поток — ветвь узла решения, исполнитель шага — дорожка (Посетитель, Web-клиент, Сервер,
   Администратор). Параллельные действия после фиксации транзакции показаны узлами `fork`/`join`, цикл перебора
   очереди — циклом с выходом `break`.
3. **Состояния.** Состояния взяты из перечислений модели данных (`BookingStatus`, `WaitlistStatus`, статус
   занятия), события переходов — из прецедентов (вызовы `book()`, `cancel()`, `promoteFirst()`) и времени
   (`when(now ≥ …)`), сторожевые условия — из правил `BookingPolicy` (представление 006). Подсостояния «Свободная /
   Поздняя отмена» и «Есть места / Мест нет» введены, чтобы сделать видимыми правила REQ-FUNC-008 и REQ-FUNC-011.
4. **Последовательность.** Линии жизни соответствуют модулям представления 002 и стереотипам анализа
   (`boundary` — SPA, `control` — контроллер и сервисы, `entity` — доменные объекты, `database` — PostgreSQL).
   Сообщения — это операции REST API (представление 004) и порты модулей; ветви `alt` совпадают с узлами решения
   диаграммы активности; `ref` ссылается на прецеденты UC-02 и UC-06; ограничение длительности — REQ-PERF-002.

### Механизмы связи между моделями

| Связь | Как обеспечивается |
|-------|--------------------|
| Требование → прецедент | столбец «Требования» в таблице прецедентов `use-cases.md` |
| Прецедент → активность / последовательность | комментарий в начале `.puml` перечисляет реализуемые UC; таблица раздела 4 `use-cases.md` |
| Активность ↔ последовательность | одинаковые условия ветвлений (`нет мест`, `пересечение`, `срок истёк`) и одинаковые операции |
| Состояния ↔ данные | имена состояний совпадают с перечислениями `data-model.sysml`; переход = операция сервиса |
| Диаграммы → SDD | представления 005, 007, 012, 013 ссылаются на файлы `docs/uml` |
| Диаграммы → ADR | блокировка `FOR UPDATE` (ADR-0004) и продвижение очереди в транзакции отмены (ADR-0006) видны на `sequence-*` и `activity-cancel` |

Пересмотреть решение, если команда перейдёт на инструмент, генерирующий диаграммы из кода, или если преподаватель
потребует единый язык SysML v2 для всех моделей.
