# Пессимистическая блокировка строки занятия при записи

## Контекст и постановка задачи

Главный риск FitSchedule — переполнение зала и двойные записи. SRS требует: при 100 одновременных запросах на
последнее место создаётся не более одной записи (REQ-REL-001, раздел 3.5.9), запись завершается не более чем за
2 с при 50 одновременных запросах (REQ-PERF-002), записи одного посетителя не пересекаются (REQ-FUNC-009). Как
синхронизировать конкурентные запросы на одно занятие?

## Драйверы решения

* REQ-REL-001 — ни одного переполнения;
* REQ-PERF-002 — 95-й процентиль ≤ 2 с;
* корректность при нескольких экземплярах приложения в будущем;
* простота для junior-разработчика.

## Рассмотренные варианты

* `SELECT … FOR UPDATE` строки `training` в транзакции записи;
* оптимистическая блокировка `@Version` с повтором при конфликте;
* уровень изоляции `SERIALIZABLE` с повтором;
* `synchronized` / `ReentrantLock` в JVM.

## Итог решения

Выбран вариант «`SELECT … FOR UPDATE`», потому что он гарантирует REQ-REL-001 без цикла повторов, а очередь из
50 запросов на одну строку при транзакции < 50 мс укладывается в 2 с.

### Последствия

* Хорошо, потому что проверка мест и пересечений выполняется под блокировкой — гонок нет.
* Хорошо, потому что работает при нескольких экземплярах приложения (блокировка в БД).
* Плохо, потому что запросы на одно занятие выстраиваются в очередь; нужен таймаут ожидания 2 с.
* Плохо, потому что нужен единый порядок блокировок (training → booking → waitlist), иначе возможны deadlock.

### Подтверждение

Интеграционный тест (Testcontainers): 100 параллельных запросов на последнее место — ровно одна запись
`CONFIRMED`, `free_places = 0`. Нагрузочный тест F-17 подтверждает 95-й процентиль ≤ 2 с.

## Плюсы и минусы вариантов

### `SELECT … FOR UPDATE`

* Хорошо, потому что поведение предсказуемо и легко объясняется.
* Нейтрально, потому что блокирует только одну строку занятия, а не таблицу.

### `@Version` с повтором

* Хорошо, потому что без ожидания при низкой конкуренции.
* Плохо, потому что за последнее место 100 запросов дают до 99 повторов и рост времени отклика.

### `SERIALIZABLE`

* Хорошо, потому что СУБД сама находит конфликты.
* Плохо, потому что откат и повтор нужен всем операциям, сложно тестировать.

### `synchronized` в JVM

* Хорошо, потому что проще всего написать.
* Плохо, потому что не работает при двух экземплярах и при прямых изменениях в БД.

## Дополнительная информация

SDD: представления 005, 006, 008. Слоты тренеров защищены уникальным `trainer_slot.booked_by` (REQ-FUNC-016).
