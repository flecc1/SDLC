# Клиент React SPA поверх REST API

## Контекст и постановка задачи

SRS требует web-интерфейс с адаптивной вёрсткой от 360 до 1920 px (REQ-INT-001) и REST API в формате JSON с
описанием OpenAPI 3.0, через которое выполнимы все операции интерфейса (REQ-INT-006). Интерфейс должен сразу
показывать результат записи и актуальное число мест (REQ-INT-002) и обновлять счётчик уведомлений без перезагрузки
страницы (REQ-FUNC-021). Как построить клиентскую часть, чтобы не реализовывать одни и те же операции дважды?

## Драйверы решения

* REQ-INT-006 — все операции через REST API;
* REQ-INT-001/002 — адаптивность и мгновенный результат операции;
* опыт исполнителя с React и Java;
* трудоёмкость: одна реализация бизнес-операций.

## Рассмотренные варианты

* React SPA (Vite) + REST API;
* серверный рендеринг Thymeleaf + Spring MVC;
* Vaadin (UI на Java).

## Итог решения

Выбран вариант «React SPA + REST API», потому что интерфейс сам является клиентом того же API, которое требует
REQ-INT-006, и операции не дублируются в контроллерах страниц.

### Последствия

* Хорошо, потому что API проверяется уже при разработке интерфейса, а OpenAPI генерируется из контроллеров.
* Хорошо, потому что обновление числа мест и счётчика уведомлений не требует перезагрузки страницы.
* Плохо, потому что нужна отдельная сборка клиента (Vite) и защита CSRF для cookie-сессии.
* Плохо, потому что первая загрузка страницы тяжелее, чем при серверном рендеринге (контролируется REQ-PERF-001).

### Подтверждение

Статические файлы SPA собираются в `fitschedule.jar` и отдаются тем же приложением; каждый экран макетов SRS
работает только через маршруты `/api/**` (контроль в ревью и e2e-тестах F-17); `/v3/api-docs` проходит валидацию.

## Плюсы и минусы вариантов

### React SPA + REST API

* Хорошо, потому что один контракт для интерфейса и интеграций.
* Нейтрально, потому что требует знания JavaScript/TypeScript.

### Thymeleaf + Spring MVC

* Хорошо, потому что меньше JavaScript и встроенная защита CSRF.
* Плохо, потому что для REQ-INT-006 пришлось бы поддерживать второй набор REST-контроллеров (+6 ч).

### Vaadin

* Хорошо, потому что весь интерфейс на Java.
* Плохо, потому что состояние UI хранится на сервере (больше памяти) и REST API всё равно нужен отдельно.
