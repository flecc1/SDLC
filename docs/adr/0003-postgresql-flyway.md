# PostgreSQL 16 с миграциями Flyway

## Контекст и постановка задачи

SRS (раздел 2.3) предписывает реляционную СУБД, предпочтительно PostgreSQL. Данные FitSchedule связаны
(пользователь — занятие — запись — лист ожидания), запись на занятие должна быть атомарной с уменьшением числа мест
(REQ-REL-001), повторная активная запись одного посетителя на одно занятие недопустима, время занятий хранится с
часовым поясом. Какую СУБД и способ ведения схемы выбрать?

## Драйверы решения

* ограничение SRS 2.3;
* блокировки строк и транзакции (ADR-0004);
* частичные уникальные индексы (`WHERE status = 'CONFIRMED'`);
* `timestamptz` для времени занятий;
* воспроизводимое развёртывание схемы (REQ-INST-001).

## Рассмотренные варианты

* PostgreSQL 16 + Flyway;
* MySQL 8 + Flyway;
* MongoDB.

## Итог решения

Выбран вариант «PostgreSQL 16 + Flyway», потому что он соответствует ограничению SRS и даёт частичные индексы,
`CHECK`-ограничения, `SELECT … FOR UPDATE` и `timestamptz`.

### Последствия

* Хорошо, потому что правила целостности (вместимость, уникальность записи и слота) проверяет сама БД.
* Хорошо, потому что схема воспроизводится миграциями `V1__…` при каждом запуске.
* Плохо, потому что интеграционные тесты требуют контейнера PostgreSQL (Testcontainers), а не H2.

### Подтверждение

Миграции применяются при старте приложения; тест Testcontainers проверяет `CHECK (free_places BETWEEN 0 AND
capacity)` и частичный уникальный индекс `booking`.

## Плюсы и минусы вариантов

### PostgreSQL 16 + Flyway

* Хорошо, потому что богатые ограничения целостности и зрелые блокировки.
* Нейтрально, потому что администрирование чуть сложнее, чем у встроенных БД.

### MySQL 8 + Flyway

* Хорошо, потому что широко распространена.
* Плохо, потому что нет частичных индексов — уникальность активной записи пришлось бы держать в коде.

### MongoDB

* Хорошо, потому что гибкая схема.
* Плохо, потому что противоречит ограничению SRS 2.3 и усложняет атомарность «запись + место».
