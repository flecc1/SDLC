# Модульный монолит на Spring Boot вместо микросервисов

## Контекст и постановка задачи

FitSchedule — учебный проект: его реализует один студент (с итерации I2 — плюс junior на учебной практике) за 6 итераций по 2 недели весеннего семестра 2027, объём — 100 ч.
Приложение разворачивается на одном учебном сервере 2 vCPU / 2 ГБ командой `docker compose up` (REQ-INST-001),
серверная часть — Java + Spring Boot (SRS 2.3). Правила бронирования должны быть независимы от web-слоя и покрыты
тестами не менее чем на 80 % (REQ-MAINT-002). Как разделить систему на части, чтобы уложиться в срок и ресурсы и
не смешать бизнес-правила с инфраструктурой?

## Драйверы решения

* срок 02.05.2027 и ёмкость команды 96–119 ч;
* ресурсы сервера 2 ГБ памяти;
* запуск одной командой (REQ-INST-001);
* независимость модуля бронирования (REQ-MAINT-002, SRS 3.5.5);
* согласованность записи и вместимости в одной транзакции (REQ-REL-001).

## Рассмотренные варианты

* модульный монолит на Spring Boot;
* микросервисы (расписание, запись, уведомления) с отдельными БД;
* слоистый монолит без модулей (controller / service / repository на всё приложение).

## Итог решения

Выбран вариант «модульный монолит на Spring Boot», потому что только он укладывается в срок и память сервера и
при этом сохраняет явные границы модулей (рисунок 1 SDD).

### Последствия

* Хорошо, потому что запись и изменение числа мест выполняются в одной локальной транзакции.
* Хорошо, потому что одно приложение и одна БД — один `docker compose up`.
* Хорошо, потому что модуль `booking` можно вынести в отдельный сервис позже, не меняя его правил.
* Плохо, потому что модули масштабируются только вместе.
* Плохо, потому что границы модулей держатся на дисциплине и проверках ArchUnit, а не на сети.

### Подтверждение

Тест ArchUnit в CI: пакеты модулей обращаются друг к другу только через интерфейсы `*Api`, пакет
`booking.policy` не импортирует `org.springframework`. Ревью pull request при каждом новом модуле.

## Плюсы и минусы вариантов

### Модульный монолит на Spring Boot

* Хорошо, потому что минимальные накладные расходы на развёртывание и отладку.
* Хорошо, потому что транзакции ACID внутри одной БД.
* Нейтрально, потому что требует правил зависимостей между модулями.

### Микросервисы

* Хорошо, потому что сервисы масштабируются и развёртываются независимо.
* Плохо, потому что запись и вместимость оказались бы в разных сервисах — нужна распределённая транзакция или сага.
* Плохо, потому что 3–4 JVM не помещаются в 2 ГБ памяти, а настройка сети и наблюдаемости съедает 15–20 ч — пятую часть всего проекта.

### Слоистый монолит без модулей

* Хорошо, потому что быстрее всего стартовать.
* Плохо, потому что правила записи растекаются по общим сервисам, и REQ-MAINT-002 становится трудно проверить.
