## 1. Введение

Документ описывает, ЧТО должен делать FitSchedule — web-приложение для записи в фитнес-клуб, а не то, КАК оно будет устроено внутри. Он адресован заказчику, разработчикам и тестировщикам проекта.

### 1.1 Назначение документа

Спецификация требований к ПО (SRS) фиксирует согласованный с заказчиком набор бизнес-, функциональных и нефункциональных требований к FitSchedule версии 0.1. Заказчик сверяет по ней полноту своих ожиданий, разработчики используют её как основу проектирования, тестировщики — для составления тестов по критериям приёмки. Документ хранится в репозитории проекта под контролем версий.

### 1.2 Область применения продукта

FitSchedule — web-приложение для посетителей фитнес-клуба. Посетитель просматривает расписание групповых занятий, видит свободные места, записывается на занятие или в слот персонального тренера, отменяет запись и ведёт краткую историю своей активности. Администратор клуба поддерживает расписание, вместимость и правила отмены, тренер видит свои слоты и записавшихся. Цель продукта — избавить посетителей от звонков и переписки при записи, а клуб — от двойных броней и переполненных залов.

В область релиза входят: учётные записи и роли; расписание групповых занятий; запись, отмена и список записей; слоты и запись к персональному тренеру; история активности; внутрисистемные уведомления об отмене занятия. Вне области текущего релиза: приём оплаты, медицинские рекомендации, синхронизация с носимыми устройствами, автоматический подбор тренировок, мобильные приложения.

## 2. Обзор продукта

### 2.1 Перспектива продукта

FitSchedule — новый самостоятельный web-продукт фитнес-клуба. Клиентская часть работает в браузере, серверная часть пишется на Java с использованием Spring Boot, данные хранятся в реляционной базе. Продукт не заменяет кассовую систему клуба и не хранит медицинские сведения. Владелец продукта — автор проекта; соглашение об уровне обслуживания (SLA) не предусмотрено.

```
Посетитель / Тренер / Администратор ──► Web-интерфейс ──► Сервер FitSchedule (Java, Spring Boot) ──► База данных
```

### 2.2 Функции продукта

- Регистрация, вход и разграничение ролей (посетитель, тренер, администратор).
- Просмотр, фильтрация и поиск групповых занятий с указанием свободных мест.
- Запись на групповое занятие и отмена записи до срока, заданного администратором.
- Просмотр слотов тренера и бронирование персональной тренировки.
- Управление расписанием, вместимостью и слотами тренеров (администратор).
- Просмотр тренером своих слотов и записавшихся посетителей.
- История активности и сводка за неделю и месяц.
- Внутрисистемные уведомления об отмене или изменении занятия.
- Напоминание о предстоящем занятии за 2 часа до начала.

### 2.3 Ограничения продукта

- Серверная часть должна быть написана на Java с использованием Spring Boot (обязательное, по заданию заказчика).
- Продукт должен быть web-приложением и работать в современных браузерах (обязательное).
- Данные должны храниться в реляционной СУБД; предпочтительна PostgreSQL (предпочтительное).
- Интерфейс и документация — на русском языке.
- Любые операции с расписанием доступны только роли «Администратор» (обязательное, см. REQ-FUNC-003).
- Внешние сервисы календаря и уведомлений не являются обязательной частью версии 1.0.

### 2.4 Характеристики пользователей

| Класс | Описание | Частота и цели |
|-------|----------|----------------|
| Посетитель | Клиент клуба без специальной технической подготовки; пользуется с телефона и компьютера | Несколько раз в неделю: посмотреть расписание, записаться, отменить запись, добавить активность |
| Тренер | Сотрудник клуба, ведёт групповые и персональные тренировки | Ежедневно: проверить свои слоты и список записавшихся |
| Администратор | Сотрудник клуба, отвечающий за расписание | Регулярно: создание и изменение занятий, вместимости, слотов и сроков отмены |

### 2.5 Допущения и зависимости

| Допущение / зависимость | Влияние, если не выполняется |
|--------------------------|------------------------------|
| Клуб предоставляет актуальные данные о тренерах, залах и расписании | Посетители видят устаревшее расписание; растёт число ручных отмен |
| Администратор своевременно задаёт срок свободной отмены | Действует значение по умолчанию; возможны споры о поздней отмене (см. открытые вопросы) |
| У каждого посетителя есть адрес электронной почты | Регистрация невозможна |
| Для внешнего API календаря заранее выбран поставщик и проверены условия доступа | Интеграция переносится в следующий релиз (REQ-INT-007) |

## 3. Требования

Формат идентификатора: REQ-[ОБЛАСТЬ]-[NNN]. Приоритет: M — обязательно, S — желательно, C — возможно. Метод верификации по умолчанию — «Тест»; иные методы указаны в разделе 4.

### 3.1 Внешние интерфейсы

#### 3.1.1 Пользовательские интерфейсы

| ID | Требование | Приоритет | Критерий приёмки |
|----|-----------|-----------|------------------|
| REQ-INT-001 | Система должна предоставлять web-интерфейс на русском языке с адаптивной вёрсткой для ширины окна от 360 до 1920 px. | M | При ширине 360, 768, 1366 и 1920 px нет горизонтальной прокрутки; расписание и кнопка записи доступны без дополнительных действий. |
| REQ-INT-002 | Система должна после каждой записи или отмены показывать пользователю понятный результат операции и актуальное число свободных мест. | M | После операции на экране виден статус («Подтверждена» / «Отменена» / причина отказа) и обновлённое число мест. |
| REQ-INT-003 | Система должна предоставлять фильтры расписания по дате, виду занятия и тренеру, а также поиск по названию. | S | После применения фильтра в списке остаются только подходящие занятия; сброс фильтра возвращает полный список. |
| REQ-INT-004 | Карточка занятия должна показывать время, зал, тренера и число свободных мест из общего числа. | M | Каждая карточка в расписании содержит все четыре поля; число мест совпадает с данными в БД. |
| REQ-INT-005 | Ошибки ввода должны сопровождаться текстовым сообщением рядом с полем, а пустые списки — подсказкой, что делать дальше. | S | Некорректная форма не отправляется и показывает причину; у нового посетителя в «Моих записях» выводится подсказка со ссылкой на расписание. |

Не применимо: система не взаимодействует с аппаратурой напрямую.

|----|-----------|-----------|------------------|
| REQ-INT-006 | Система должна предоставлять REST API в формате JSON, описанное спецификацией OpenAPI 3.0. | M | Спецификация доступна по адресу /v3/api-docs и проходит валидацию без ошибок; все операции интерфейса выполнимы через API. |

### 3.2 Функциональные требования

##### Учётные записи и роли

| ID | Требование | Приоритет | Критерий приёмки |
|----|-----------|-----------|------------------|
| REQ-FUNC-001 | Система должна позволять посетителю зарегистрироваться по имени, адресу электронной почты и паролю (не менее 8 символов, буква и цифра). | M | Корректные данные создают учётную запись; повторный email и слабый пароль отклоняются с сообщением. |
| REQ-FUNC-002 | Система должна предоставлять вход и выход; срок действия сессии должен быть ограничен (не более 7 суток). | M | После выхода закрытые страницы требуют повторного входа; по истечении 7 суток вход запрашивается заново. |
| REQ-FUNC-003 | Система должна поддерживать три роли (посетитель, тренер, администратор) и ограничивать административные операции ролью администратора. | M | Запрос посетителя или тренера на создание или изменение занятия отклоняется с кодом 403. |

##### Расписание и групповые занятия

| ID | Требование | Приоритет | Критерий приёмки |
|----|-----------|-----------|------------------|
| REQ-FUNC-004 | Система должна отображать групповые занятия за выбранную дату или неделю. | M | Пользователь видит название, время, зал, тренера и число свободных мест для каждого занятия выбранного периода. |
| REQ-FUNC-005 | Администратор должен создавать групповое занятие с названием, датой, временем, залом, тренером и вместимостью. | M | Новое занятие сразу отображается в расписании; вместимость — целое число больше нуля. |
| REQ-FUNC-006 | Администратор должен изменять и отменять занятие. | M | Изменение отображается в расписании; при отмене занятие получает статус «Отменено», а все его записи — статус «Отменена клубом». |
| REQ-FUNC-007 | Система должна разрешать посетителю записаться на занятие при наличии свободных мест. | M | После подтверждения создаётся ровно одна запись пользователя, а число свободных мест уменьшается на единицу. |
| REQ-FUNC-008 | Система не должна записывать посетителя на занятие, где нет свободных мест. | M | Запрос отклоняется с понятной причиной, число мест не меняется. |
| REQ-FUNC-009 | Система не должна создавать записи одного посетителя, пересекающиеся по времени. | M | При попытке записаться на пересекающееся занятие показывается причина отказа и конфликтующая запись. |
| REQ-FUNC-010 | Посетитель должен видеть список своих предстоящих и отменённых записей. | M | Список содержит статус, дату, время и название занятия; предстоящие и отменённые разделены вкладками. |
| REQ-FUNC-011 | Посетитель должен иметь возможность отменить запись до срока, заданного администратором. | M | До наступления срока статус меняется на «Отменена», место возвращается в расписание; после срока кнопка недоступна. |
| REQ-FUNC-012 | Администратор должен задавать срок свободной отмены (в часах до начала) для занятия. | S | Заданный срок отображается в подтверждении записи и в списке «Мои записи». |
| REQ-FUNC-013 | Администратор должен иметь возможность отменить запись посетителя после истечения срока свободной отмены. | S | После отмены администратором запись получает статус «Отменена», место возвращается; действие фиксируется в журнале. |

##### Персональные тренировки

| ID | Требование | Приоритет | Критерий приёмки |
|----|-----------|-----------|------------------|
| REQ-FUNC-014 | Администратор должен задавать доступные слоты каждого тренера. | M | Созданный слот появляется в профиле тренера и в списке свободных слотов. |
| REQ-FUNC-015 | Посетитель должен просматривать свободные слоты выбранного тренера. | M | Выводятся только свободные слоты в будущем; занятые отображаются недоступными или скрыты. |
| REQ-FUNC-016 | Посетитель должен бронировать свободный слот тренера; один слот не может быть забронирован двумя посетителями. | M | После подтверждения слот недоступен другим; при двух одновременных запросах на один слот успешно выполняется ровно один. |
| REQ-FUNC-017 | Тренер должен видеть список своих ближайших слотов и записавшихся посетителей. | S | Тренер видит только собственные слоты и занятия; запрос чужого расписания возвращает 404. |

| ID | Требование | Приоритет | Критерий приёмки |
|----|-----------|-----------|------------------|
| REQ-FUNC-018 | Посетитель должен добавлять завершённую активность с датой, типом и длительностью. | S | Корректная запись появляется в истории активности; длительность — целое число минут от 1 до 600. |
| REQ-FUNC-019 | Система должна показывать историю активности и краткую сводку за неделю и месяц (число тренировок, суммарное время). | S | Для тестового набора записей значения сводки совпадают с ручным расчётом. |
| REQ-FUNC-020 | Система может автоматически включать в историю активности посещённые групповые и персональные занятия. | C | Прошедшая подтверждённая запись отображается в истории с пометкой «по записи»; отменённая — не отображается. |
| REQ-FUNC-021 | Система должна уведомлять участников внутри приложения об отмене или изменении занятия администратором. | S | Уведомление содержит название, новое или прежнее время занятия и появляется в течение минуты после изменения. |
| REQ-FUNC-022 | Система должна показывать посетителю внутри приложения напоминание о предстоящем занятии (групповом или персональном), на которое он записан, за 2 часа до начала. | S | Напоминание с названием, временем и местом занятия появляется в интерфейсе за 2 часа до начала (допустимое отклонение — 1 минута) или при следующем открытии сайта, если посетитель был вне его; для отменённой записи и для записи, сделанной менее чем за 2 часа до начала, оно не создаётся; для одной записи показывается один раз. |

### 3.3 Качество обслуживания

#### 3.3.1 Производительность

| ID | Требование | Приоритет | Критерий приёмки |
|----|-----------|-----------|------------------|
| REQ-PERF-001 | Страница расписания должна загружаться не более чем за 3 секунды при 200 занятиях за неделю. | S | Среднее из 20 измерений не превышает 3 с. |
| REQ-PERF-002 | Операция записи должна завершаться не более чем за 2 секунды при 50 одновременных запросах. | M | 95-й процентиль не превышает 2 с; двойных записей нет. |
| REQ-PERF-003 | Главная страница должна быть доступна не позднее чем через 4 секунды после холодного запуска сервиса. | S | Среднее из 5 запусков не превышает 4 с. |

#### 3.3.2 Безопасность

| ID | Требование | Приоритет | Критерий приёмки |
|----|-----------|-----------|------------------|
| REQ-SEC-001 | Пароли должны храниться только в виде хэша BCrypt со стоимостью не ниже 10. | M | В БД отсутствуют пароли в открытом виде; параметр стоимости в хэше не меньше 10. |
| REQ-SEC-002 | Система должна передавать данные между клиентом и сервером только по HTTPS (TLS 1.2 и выше). | M | HTTP-запрос перенаправляется на HTTPS; сканер не обнаруживает поддержки TLS ниже 1.2. |
| REQ-SEC-003 | Пользователь должен иметь доступ только к собственным данным; обращение к чужой записи или чужому расписанию не допускается. | M | Автотест: пользователь A запрашивает по id записи пользователя B — всегда отказ (404 или 403). |
| REQ-SEC-004 | Система должна проверять вводимые даты, время, вместимость и длительность на стороне сервера. | M | Некорректный ввод (дата в прошлом, вместимость ≤ 0, окончание раньше начала) отклоняется с сообщением и не вызывает сбоя. |
| REQ-SEC-005 | Журналы не должны содержать пароли, токены и секреты внешних сервисов. | S | Поиск по журналу за сутки не находит паролей и токенов. |

#### 3.3.3 Надёжность

| ID | Требование | Приоритет | Критерий приёмки |
|----|-----------|-----------|------------------|
| REQ-REL-001 | Система должна сохранять целостность вместимости при конкурентных запросах на запись. | M | При 100 одновременных запросах на последнее место создаётся не более одной записи. |
| REQ-REL-002 | Система должна корректно обрабатывать сетевые ошибки без аварийного завершения. | S | При обрыве соединения пользователь видит сообщение, приложение продолжает работу, данные не искажаются. |
| REQ-REL-003 | При отмене занятия все связанные записи должны получить согласованный статус отмены. | M | После отмены занятия у всех участников одинаковый статус; числа мест и записей согласуются. |

#### 3.3.4 Доступность

Отдельные требования к доступности не заданы: SLA не предусмотрен (см. 2.1).

#### 3.3.5 Наблюдаемость

| ID | Требование | Приоритет | Критерий приёмки |
|----|-----------|-----------|------------------|
| REQ-OBS-001 | Система должна журналировать создание, отмену и отклонение записи (время, событие, технический идентификатор). | S | Журнал содержит три указанных поля для каждого события; персональные данные в нём отсутствуют. |

### 3.5 Проектирование и реализация

#### 3.5.1 Установка

| ID | Требование | Приоритет | Критерий приёмки |
|----|-----------|-----------|------------------|
| REQ-INST-001 | Система должна разворачиваться командой docker compose up (приложение и PostgreSQL); настройки и секреты передаются переменными окружения. | M | На чистой машине с Docker приложение доступно не позднее чем через 5 минут; в репозитории нет паролей и токенов. |

#### 3.5.2 Сборка и поставка

| ID | Требование | Приоритет | Критерий приёмки |
|----|-----------|-----------|------------------|
| REQ-BUILD-001 | Система должна собираться Maven в исполняемый JAR (Java LTS) и образ Docker; для каждого pull request CI выполняет сборку и тесты. | S | Проверка GitHub Actions в pull request проходит; сборка воспроизводима. |

#### 3.5.3 Распределение

Система разворачивается как один экземпляр приложения и одна БД; горизонтальное масштабирование в текущем релизе не требуется.

#### 3.5.4 Сопровождаемость

| ID | Требование | Приоритет | Критерий приёмки |
|----|-----------|-----------|------------------|
| REQ-MAINT-001 | Исходный код и документация должны храниться в Git; изменения требований проходят через отдельную ветку и pull request. | S | В истории есть ветка, pull request и проверяемые коммиты. |
| REQ-MAINT-002 | Модуль бронирования должен быть независим от web-слоя, а его тестовое покрытие — не менее 80 % строк. | S | Отчёт покрытия (JaCoCo) для модуля бронирования показывает не менее 80 %. |

#### 3.5.5 Повторное использование

Модуль бронирования отделяется от web-слоя, чтобы его правила (вместимость, пересечения, сроки отмены) можно было применять и в других клиентах.

#### 3.5.6 Переносимость

Система должна работать на любой ОС, где есть Docker или JDK соответствующей LTS-версии; привязка к конкретному облачному провайдеру не допускается.

#### 3.5.7 Стоимость

Разработка и размещение не требуют затрат: используется бесплатное ПО и учебная инфраструктура.

#### 3.5.8 Сроки

Сроки определяются графиком курса «Жизненный цикл разработки ПО»: SRS (лабораторная работа № 3) — октябрь 2026; MVP 0.1 — по графику следующих лабораторных работ; точные даты уточняются у преподавателя.

#### 3.5.9 Доказательство концепции

До полной реализации проверяется прототип бронирования: при 100 одновременных запросах на одно последнее место создаётся не более одной записи (REQ-REL-001). Результат определяет выбор способа блокировки в БД.

#### 3.5.10 Управление изменениями

Работа ведётся в ветках Git с обязательным pull request и ревью; версии нумеруются по SemVer; изменения требований записываются в историю изменений документа.

### 3.6 ИИ/МО

Не применимо: в версии 1.0 не используются обучаемые модели; автоматический подбор тренировок вынесен за рамки релиза.
